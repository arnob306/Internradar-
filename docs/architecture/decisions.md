# Decision log

Product decisions that resolve the open questions in the [architecture overview](overview.md) and the [test plan](../testing/test-plan.md). Recorded 2026-09-30. Where this log and the overview disagree, this log wins.

| ID | Decision | Choice | Why |
|---|---|---|---|
| D1 | Definition of `cycle_year` | The calendar year the program **starts**. | It is part of the unique keys on `program_windows` and `applications`, so it needs one unambiguous meaning. Default program start months derive from it (vacationer and internship: Nov; graduate: Feb). |
| D2 | Discipline vocabulary | Freeze about 15 controlled terms plus a `stem_any` group. Extracted text that doesn't map to a term gives `unknown`. | The engine never guesses a discipline. Adding terms later requires a migration of the rules JSON. |
| D3 | Citizenship | Optional profile field. If it's blank, citizenship criteria evaluate to `unknown`. Never logged and never written to `metrics_events`. | It is sensitive personal information (Australian Privacy Principles). A missing value must not produce a false "eligible" or "ineligible". |
| D4 | Mid-year graduates and honours | One semester remaining gives `unknown` with reason `MID_YEAR_GRADUATE_CHECK_EMPLOYER`, unless the program's rules set `acceptsMidYearGraduates`. Onboarding asks "Are you planning to do honours?" and uses the graduation date of the last degree. | Employers treat mid-year graduates inconsistently, so the honest answer is "check with the employer". Honours intent changes the graduation date, which changes the year level. |
| D5 | Year-level model | The semester model: S1 runs Feb–Jun and S2 runs Jul–Nov. Year level is the number of semesters remaining, measured against the program window's start date (§4). This replaces the TDD plan's Feb–Dec academic-year assumption. | It handles mid-year graduation and double degrees. Trimester universities are out of scope for cycle 1. |
| D6 | Alert targeting | P5 alerts go only to users who follow or saved the program. Eligibility-based targeting waits for v2. | It keeps the dispatcher off `profiles` and keeps alert volume low while human review is the bottleneck. |
| D7 | Who creates alerts | Only the server (the `alert_dispatcher` role) inserts or updates alerts. Users can read their own alerts and change their alert preferences. | The alerts table is the delivery outbox and the source of the accuracy metrics. User writes would corrupt both. |
| D8 | Auto-accept threshold | No extraction is auto-accepted at first; every change is reviewed. After the Phase 6 eval, date-only and status-only changes with confidence of at least 0.9 **and** at or above the calibrated tau can skip review. Eligibility-rule changes are always reviewed. | Alert accuracy is the product's credibility, and tau must come from measured precision, not a guess. Refines ADR-008. |
| D9 | Tracker transitions | Forward moves only: `saved → applied → online_assessment → interview → offer`, with the online assessment skippable. `rejected` is reachable from any state except `offer`. The user can undo their most recent transition. Every change writes an `application_events` row. | Forward-only keeps the funnel metrics clean. Undo stops a misclick from stranding a user, which admin-only correction would not. |
| D9a | Where tracker rules live | Both. The TypeScript domain owns the full rules and the messages the user sees. The database also enforces the minimum: legal forward moves, a single-step undo, and events written by a trigger that clients cannot write. (Added after the Phase 1 review.) | Supabase exposes the database over a public API, so anything enforced only in the web API can be bypassed. Duplicating a small transition table in SQL is the price of that guarantee. The two tables must stay in step, and the Phase 4 tests check both. |
| D10 | Repo visibility | Public, with strict log hygiene (§6.3). | Portfolio value. Because GitHub Actions logs are public, workers log IDs only, never email addresses. |
| D11 | Admin and review load | One admin (the maintainer), in a single `app_admins` row. The README states a 48-hour review turnaround. | It's a solo project. Promising a turnaround that can actually be met is better than a 24-hour target that slips. |
| D12 | Page text retention | Keep normalised page text (`norm_text`) for 90 days, then purge it weekly. Evidence quotes are kept. | Reviewers and the eval need context. The 90-day limit bounds storage and republishing risk (ADR-013). |
| D13 | Seed employer ATS audit | Do it as a Phase 0 spike before sizing Phase 3: record which seed employers use Greenhouse, Lever, Workday or a bespoke page. **Done 2026-09-30:** 3 of 16 employers had a board (Optiver and IMC on Greenhouse, KPMG on Lever). See [ats-audit.md](ats-audit.md). | If fewer than about 10 use Greenhouse or Lever, Phase 3 shrinks to the seed loader plus one adapter. The threshold was missed, so Phase 3 is the seed loader plus a Greenhouse adapter, and the Lever adapter is deferred. |
| D14 | Toolchain versions | Node 24, Python 3.13, pnpm 12, uv. TypeScript is pinned to 6.0.x. | These match the developer machine and CI, so local and CI runs behave alike. The original plan assumed Node 22 and Python 3.12. TypeScript 7.0 is excluded for now because typescript-eslint 8.71 supports only `<6.1.0`; revisit when it adds 7.x support. |
| D15 | First-cycle scope | Start with a small hand-verified seed of about 10 to 15 programs across sectors (tech, consulting, engineering, commerce, research), then grow in waves once eligibility, review and alerts work. The long-term aim is broad STEM, commerce and research coverage from allowed sources only. This replaces the earlier 50 to 100 target for the first release. | Breadth costs curation effort, and unverified data produces wrong eligibility answers and alerts. A small verified set proves the pipeline first. Keeping about 15 discipline terms is enough at this size. Widening the vocabulary and adding grade-based (WAM) rules wait until the seed grows. Aggregator sites remain off limits (ethics policy). |
| D16 | Year-level rules and graduates | A year-level rule (`penultimate`, `pre_penultimate`, `final_year`, or explicit bounds) never counts someone whose graduation is before the month it is measured: they are ineligible with `ALREADY_GRADUATED`. Programs that take recent graduates say so with a graduation window. Unverified rules give only `RULES_UNVERIFIED` and are never evaluated. Rules read from the database are parsed first, and a malformed one gives `unknown` with `RULES_INVALID`. (Added after the Phase 2 review, findings H1, M1 and L1.) | "0 semesters left" describes both someone finishing now and someone who finished years ago, so a stale profile date made a graduate look like a final-year student. A wrong "yes" is the one error the engine must not make. Malformed rules must never break a page of results. |
| D17 | Sign-in method | Magic link by email only for the MVP, through Supabase Auth. No passwords and no social login yet. | There are no passwords to store, leak or reset, and no OAuth app to register or review. Students already live in their university inbox. Supabase issues the same user id for any later provider, so adding Google sign-in later changes no tables. |
| D18 | Student outcome reports | Post-MVP, after Phase 4. Students can share an application outcome (stage reached, degree area, WAM band, study year) anonymously. Only aggregates are ever shown, and only for groups of at least 5 reports. WAM is stored as a band, never an exact number. No free-text reviews at first. Reports are opt-in, tied to a signed-in account, deleted with the account, and covered by the privacy notice. | It answers the question employer pages leave open (what WAM got people in), and it would feed the Phase 7 insights. Risks are re-identification, fake reports and cold start, so the group-size rule is enforced in the database and nothing is shown until enough reports exist. The tracker already records stage and resume per application, so a report can pre-fill from it. |
| D19 | Opening-dates timeline | A single page, built right after the tracker, laying out when upcoming applications open and close along one time axis, from the same window data the program pages use. The problem it solves: large companies rarely announce when they open, so students (the author and their peers) cannot plan. So the page shows confirmed dates and also "usually opens around..." estimates from one or two past cycles that the author looks up by hand, each with its source. Confirmed dates and estimates must look different, and the page never shows a date more precisely than the evidence gives. Programs with neither are listed separately as "no date yet" rather than guessed. Signed-in students see their saved programs highlighted. Predictions computed automatically from a longer history stay in Phase 7 and layer onto this same page. | Students plan around opening dates, and one page showing the whole season is more useful than opening each program. The data and precision rules already exist (window status, precision labels), so this is mostly a view. Predicting future dates from past years stays in v2. |
| D20 | Rate limit on the public program API | `GET /api/v1/programs` and `GET /api/v1/programs/{company}/{program}` allow one client 60 requests a minute between them, counted in the server's own memory by the proxy's client address (`x-real-ip`, else the first `x-forwarded-for` entry, else one shared bucket) and refused with `429 RATE_LIMITED` and a `Retry-After` header. The table of clients is capped (10,000, then one shared overflow bucket) so it cannot be used to fill memory. The pages themselves are not limited. This is a guard, not a guarantee: each server instance counts on its own, and an address header can be forged when a request does not pass through a trusted proxy, so a platform-level limit is still to be set when the site is deployed. | The existing database limiter counts per signed-in student and has to refuse visitors, and counting every anonymous request in the database would let an attacker make us write rows. An in-memory limit costs nothing per request and stops one caller hammering the catalogue, which is all this API needs today. A CDN already absorbs repeat reads of the same URL for a minute; this covers callers who vary the URL. |
| D21 | The calendar leads the product | InternRadar's headline job is telling a student when graduate and internship programs open and close, so they can plan applications before they miss them. The opening-dates timeline becomes the home page and the program cards move to their own Programs page. Eligibility checking stays (on program cards and detail pages) but is secondary, and no new eligibility work is planned ahead of dates, the timeline, alerts and history. Students can narrow the timeline by stream: program type, field of study and industry. | The author's own problem, and the reason the project exists, is not knowing when large employers open. Eligibility answers a different question ("can I apply?") that students ask after they know a program is open. Leading with the calendar makes the product's purpose clear at a glance. |
| D22 | How sure a date is, and when to start preparing | Every timeline entry carries one of three labels: **Confirmed** (the employer stated an opening as a day or a month, or the program is open now), **Estimated** (a guess from one or two past cycles, never drawn or worded as a stated date), or **Not announced** (nothing usable, including an upcoming program with no stated opening). Each entry also gets one plain "what to do next" sentence. Preparation is advised to start 28 days (four weeks) before the earliest day the program could open: a day-precision opening uses that day, a month-precision opening uses the 1st of the month, and an estimate names only a month ("Start preparing around July"). If that date has already passed, it says to start now. A program with no date says so and points to the employer's page; it does not promise alerts until alerts exist. | Students need an action, not only a calendar. One fixed lead keeps the advice simple and honest; four weeks covers a cover letter, practice assessments and a resume refresh. Basing it on the earliest possible opening, and never on an estimate, keeps the "never more precise than the source" rule (D19) intact. |
| D23 | Industry filter | A program may carry one optional **industry**: `banking_finance`, `consulting`, `technology`, `engineering_resources`, `government_defence` or `other`. It is stored as a nullable enum column (`programs.industry`), where null means the program has not been tagged, and it is written only by the seed file. The home timeline and the Programs list each get a second row of plain links, "Filter by industry", that combines with the type filter and keeps it. The choice lives in the address (`?industry=consulting`), so it works without JavaScript and can be shared, and the current link carries `aria-current`. An industry that is repeated, empty or not offered is ignored and the home page says the filter wasn't valid. A filter with no programs names itself, for example "No vacationer programs in Consulting to show yet." The public API takes `industry` as a query parameter, returns it on every program, and `openapi.yaml` documents both. A program that has not been tagged shows only under "All industries". The 13 seed programs are tagged by employer: the four banks as banking and finance, the four consulting firms as consulting, Atlassian as technology, the Australian Public Service as government and defence. | D21 promised streams by program type, field of study and industry. Type and field already existed, and a student who thinks "I want a bank" or "I want consulting" had no way to say so. One industry per program is enough because each employer here fits one, and a list of tags would invite arguments about where a program belongs. An enum, not free text, so a typo can never become a filter that matches nothing. The author chose "consulting" over "professional services" because it is the word students search for. Tags are data in the seed, reviewed in a pull request, not guessed in code from a company name. The cost is a second row of filters, which moves the first chart row about 44px lower on a 1280x720 screen (495px, from 451px), so the "Browse all programs" link now sits beside the type filter to keep that small. |
| D24 | Student-reported process timelines (planned, not built) | After the calendar is trustworthy, students may report what happened in a program's process, as a **structured report, not a free-text review**: the stage reached, the dates of the assessment invite, interview and offer, the kinds of assessment (by name only), the outcome, and an optional short tip. Rules fixed now: no questions or answers from assessments (employers treat them as confidential and it is unfair to other candidates); no free text about named people; reporting needs a signed-in student with a verified student email; reports are moderated before they show; results appear only as aggregates once at least 5 students have reported for the same program and year; contributions are covered by delete-my-data and by a rate-limit bucket; and legal advice on defamation and confidentiality is taken before launch. D23 is reserved for the industry stream (timeline Step 2). | Glassdoor already hosts general Australian graduate interview data (stage mix, difficulty, time to hire for employers such as ANZ, Telstra and BHP), so "share your interview" alone is not a gap. What is missing is timing per program and per year, tied to the calendar: when invites and offers actually arrived. That extends the product's own problem (not knowing when) past the opening date. The costs are real: an empty page for the first students, legal risk with named employers, and fake reports, so it waits until the calendar brings traffic and is built structured, verified and aggregated. |
| D25 | Application stages on the program page | A program may carry an optional, ordered list of **application stages**: the steps the employer's own page describes (for example online application, video interview, assessment centre). Each stage is a name, an optional one-line description, and a **source link that is required**; the page shows a stage only if it has a safe source, and shows "stages aren't published here yet" when there are none. It is stored as `programs.application_stages` (jsonb, a list, default empty), written only by the seed file, read through row-level security like the rest of the program, and also returned by the public API. No stage text, link or order is invented: the seed parser refuses a stage with no source, an aggregator link, an unknown key, or more than 12 stages, and the page re-checks each value it reads. The apply link moves into the same section, so "how to prepare" and "go and apply" sit together. | It answers the second half of the student's problem (knowing how to prepare, not only when) without taking on the risks of student-written content (D24). Requiring a source for every stage keeps the project's rule that the site never states more than the employer's page proves. A jsonb list is enough at this size; a separate table would add joins for a list that is always read whole. |
| D26 | Home timeline filter by program type | The home timeline can be narrowed to **Graduate** or **Vacationer** with plain links (`/?type=graduate`, `/?type=vacationer`) beside "All programs". The choice lives in the address, so it works without JavaScript and can be shared, and the current link carries `aria-current`. Only those two types are offered, because the seed holds only those two. A `type` that is repeated, empty or not offered is ignored and the page says the filter wasn't valid, with a link to all programs. Other parameters (for example tracking codes) are left alone and raise no notice. A filter with no programs says so instead of drawing an empty chart. The summary counts follow the filter. | The student's question is often "which vacationer programs can I still catch?", and one flat chart makes them scan every row. Links in the address keep the page simple, shareable and keyboard friendly, and reuse the pattern of the programs feed. Reporting an invalid value, instead of silently showing everything, keeps a mistyped link from looking like "no programs". The industry and degree-area filters are not part of this: industry needs a migration and the author's approval of the tagging (D23 is reserved for it). |
| D27 | Add a program's dates to a calendar | A program page offers a calendar file (.ics) with one all-day event for each opening or closing date that the employer's source gives **to the day** and that has not passed (Melbourne day). Month-only and estimated dates are left out, and the page says so. Each event says the dates can change and links to the source. The file is built by a pure function (`buildCalendar`) and handed to the browser as a download link, with a stable event id so importing it again updates the event. It also holds a "start preparing" day four weeks before a day-precise opening (the lead from D22), dropped once that day has passed. It is a one-off file the student chooses to download: it is not a subscription and not an alert. | The product exists to answer "when does it open?". A calendar entry puts the answer where the student already looks, without an email sender, which does not exist yet. Leaving out month and estimated dates keeps the rule that a date is never shown more precisely than its source proves: a calendar would turn "around March" into a specific day. A subscription feed (webcal) was rejected because it implies the dates are kept up to date, which nothing here does yet. A new API route was rejected because it would widen the public API and its written spec for a feature the page can serve alone. |
